# Measured workflow

Detail for `SKILL.md`. Its hard rules apply here; nothing in this file relaxes them.

Never stop because the first rewrite, index, benchmark, or tool call loses. A timeout or a refusal is a candidate state, not a reason to abandon the session: record it, clean up when required, and continue while the time budget allows. `get_tool_guide("proving_a_rewrite")` has the reading notes for each tool; this file has the order and the rules.

## The sequence

1. **Static answer first**, from `SKILL.md`: contract frozen, the ladder's first design, complete SQL.
2. **Plan and history, only what the decision needs.** With a Query Store query id: `analyze_query_plan(query_id=...)` and, when the complaint is "it got slower", `get_query_store_trend(query_id=...)` or `get_query_store_regressions`. Without one: `explain_query`. An estimated plan cannot show what was slow; for time use `explain_query` with `analyze=true`, or `analyze_query_plan` with `last_actual=true`. Each finding names a node, its evidence, and a `family`: treat it as a lead to measure, never as proof. A `non_sargable_predicate` or `implicit_conversion_on_column` finding is a rewrite target; no index can fix it.
3. **Parameter cases.** When the request fixes the cases, use them and skip the two lookups in this step. Otherwise at most four, with real values: common, rare, NULL when valid, and a boundary value. Take them from `get_query_parameter_buckets` (what production compiled with) and `get_column_statistics` (`value_picks`); never guess a value. For a branching batch, one case per branch. Each case is `{name, values, types, weight}` with the declared SQL type of every parameter.
4. **Open the case and the session.** `start_performance_case` with the unchanged baseline SQL, one objective (`elapsed_time`, `cpu`, `logical_reads`, or `physical_reads`), the cases, and the exact `query_store_query_id` when known. `decision.by_metric` gives the verdict on CPU, elapsed time, and logical reads from the same runs: never open a new case to change the objective. Then `start_tuning_session` once; leave the limits out unless the user set a budget. One exception: when an index or a view will be built, set `time_limit_minutes` to `local_tuning_policy.max_tuning_session_minutes`, because the 20-minute default includes the build. `check_capabilities` must show `mcp_contract.performance_tuning=1`; otherwise remain in static mode.
5. **One candidate: go straight to the finalist.** `add_tuning_candidate` with the complete SQL and one strategy (`predicate`, `join`, `aggregation`, `cardinality`, `index`, `combined`, `rewrite_plus_index`), then `benchmark_tuning_candidate` with `phase=finalist`. The finalist runs the snapshot comparison itself, and the session takes more candidates afterwards. A finalist needs every registered case; a subset is for `phase=screening` only. Screen first (`phase=screening`) only when several candidates must be ranked, and screen once.
6. **Index candidates** use `benchmark_index_candidate`, never the rewrite benchmark; a test indexed view has its own tool. Read the sandbox reference first. A rewrite that is faster only with its index is one call: register it with `strategy=rewrite_plus_index` and no `artifact_ref`; the index benchmark with the original as `sql` and the rewrite as `candidate_sql` then measures the original against the rewrite with its indexes. No second case or session. Several variants on the same index or view (a second rewrite, another index in the set, a comparison call): pass `keep_for_session=true` on the first call, with every case you will need, and reuse the objects. On a table over about 5 million rows every build costs minutes, so plan the variants first. `get_tool_guide("session_held_objects")` has the rules.
7. **Read `decision`** first: the verdict, the equivalence status, and per case the speedup and the medians. Ask for `detail="full"` only when it leaves a question. Reject a candidate with a material regression in any tested case even if its total improves. When the cases differ in selectivity, run the cross case, `cross_case={"compile_case": A, "run_case": B}`. It exists on `benchmark_tuning_candidate` only. For an index candidate, pass `plan_reuse="first_case"`: all cases run on the plan that the first case compiled, in the order given. That is a shared-plan run, not a pairwise cross-case test: say which it was. `time_spent` shows where the seconds went: read it to decide whether another variant fits the budget. A `partial: true` result (the call reached `max_call_seconds`) is still evidence, and held objects stay. `run_rule` and `build_retries` explain a low run count or a retried build.
8. **Finalize.** Always: `finalize_tuning_session` drops every held object (`held_test_objects_dropped`), so never leave a session unfinalized. Call it with the selected finalist, or with no selection, and an exact stopping reason. Pass `logical_preconditions` for each constraint the rewrite depends on: the catalog verifies them, and `deployment_ready` is true only then. Each is `{kind, schema_name, table_name, columns: [...]}` with kind `not_null`, `unique`, `trusted_foreign_key`, or `trusted_check`; the tool text has each shape. Entries in `handled_by_statement` and `conditional_preconditions` never block. Never pass a declared precondition here: the catalog refutes it. `deployment_blockers` says why it is false. `selection_scope=proven` is the default; pass `selection_scope=performance_only` only on explicit user authorization, and it never implies equivalence or deployment approval.

Evidence collection is optional here. Call `collect_performance_evidence` (the case id, the same SQL, an idempotency key) only when waits, blocking, or resource pressure may explain the slowness.

## Rules that protect the result

- Pass an exact `query_store_query_id` unchanged; never match a query by nearest text.
- Parameter values stay in the conversation. The server keeps fingerprints of parameter values, never the values, so do not expect it to return them.
- A lost response is read back with `get_tuning_session`; never rerun it with a new idempotency key. A session that reports `accepts_new_work=false` is retrieval-only.
- A long call needs a client tool timeout above `check_runtime_status.timeouts.session_workflow_seconds`. On an index or view benchmark, set `max_call_seconds` from the time left in the time budget.
- Both benchmark tools time the first run of each arm and case: under 1 second, every requested run; 1 to 10 seconds, at most 3 runs; 10 seconds or more, that one run. `runs` lowers the count. Do not run the statement first only to time it.
- A baseline that ran once is kept for the session, and both benchmark tools reuse it. `slow_baseline_cases={"case": seconds}` declares such a case before the first run; it is optional. With one sample only a gain of 50% or more counts as improved. `get_tool_guide("measurement_time_rules")` has the detail.
- A budget refusal names the cap. Report it and continue inside it; do not open a second session to get around it.

## Candidate states

Every measured candidate ends in exactly one of `improved`, `neutral`, `regressed`, `equivalence_failed`, `performance_only`, `inconclusive`, or `cleanup_required`. The session outcome is a validated winner, `performance_only`, `no_change`, or `inconclusive`.

- A slower or failed index rejects only that index candidate. It never erases the paired rewrite or ends the session.
- A timeout is normally `inconclusive`. An unconfirmed index or view cleanup is `cleanup_required`: give the returned rollback DDL and start no further test index in that database.
- `performance_only` (faster, equivalence not proven) is selected only on explicit user authorization and is never deployable.
- Screening defers the comparison, so a screening result is never a winner.
- The report may recommend a design whose results matched on the tested cases, with that scope stated. The session selection still follows the rules above.

Write the answer with the client-report reference: it holds the plain words for each state and the operator appendix.
