# Profiles and budget

Detail for `SKILL.md`. Its hard rules apply here; nothing in this file relaxes them.

- **Profiles.** `check_runtime_status` returns `profile`. Null is an unprofiled server that exposes every tool group. `optimizer` (`AZURE_SQL_PROFILE=optimizer`) is read-only: rewrites, evidence, equivalence, and plan comparison. `sandbox` adds leased test indexes and gated view apply, verify, and rollback; it needs local stdio, `AZURE_SQL_TOOL_GROUPS=core,performance,admin`, and a non-production database policy. Index benchmarks run only under `sandbox`.
- **Policy.** `check_capabilities.local_tuning_policy` is authoritative: `allow_benchmark`, `allow_test_indexes`, `allow_offline_test_index`, `test_index_name_prefixes`, `allow_view_apply`, and the caps on candidates, executions, and minutes. Never widen local policy; report the exact cap and continue within it. Do not create replacement sessions to evade a budget.
- **Defaults.** `start_tuning_session` without limits takes 10 candidates, 120 measured executions (more when the parameter cases need it), and 20 minutes, each capped by policy. A limit you state above the policy is refused, so leave limits out unless the user set a budget. One exception: when an index or a view will be built, set `time_limit_minutes` to the policy's `max_tuning_session_minutes`, because the session clock includes the build.
- **Time budget.** The engagement's time budget in `SKILL.md` (the user's figure, otherwise 30 minutes) is yours to keep; the session limits are the server's caps. A high session limit is not permission to pass the time budget.
- **Runs.** `runs` is 2 to 5 paired runs per parameter case on the rewrite benchmark, and 1 or more on the index and view benchmarks; the tools lower it for a slow statement. A finalist adds one snapshot comparison. The result's `decision.executions` reports what ran: quote that, not an expected count.
- **Call cap.** `max_call_seconds` (30 or more) caps one index or view benchmark call: set it from the time left in the time budget. No run and no build starts after it. The result is then `partial: true` with no verdict: still evidence, and with `keep_for_session` what was built stays, so add a candidate and call again.
- **What a result says about time.** `time_spent` gives the seconds for baseline runs, build, candidate runs, comparison, and cleanup: read it before you plan another variant. `run_rule` `one_run_each_large_gain` means one run of each side decided, because the candidate took at most one tenth of the baseline. `build_retries` lists a build that lost a deadlock or a lock wait and was retried once.
- **"Find the fastest version".** The time budget still applies. Inside it and the policy caps, continue until 80% of it is spent, every credible candidate has a terminal state, or further search has a written diminishing-return reason. "Fastest" means the fastest candidate whose results matched on every tested parameter case: proven equivalent, or a tested match with its scope stated. Never claim a global optimum over untested SQL.
- **Timeouts.** A timeout consumes what may have run. Keep its idempotency key, read the session back, and do not retry blindly. It is `inconclusive` unless cleanup is unconfirmed. Continue with the next candidate when budget remains.
